# Migração do `cotas_dbt` (Meta 3) para a estrutura dos ADRs 0010 e 0015 — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mover os 24 modelos de `dbt/minc/models/cotas_dbt/` para pasta por fonte (`transferegov/`, `bbagil/`), `intermediate/` e `data_products/cultura_em_numeros/`, com a camada no nome do arquivo e o schema igual ao nome da pasta, **sem mudar nenhum número**.

**Architecture:** Cada `stg_*` que hoje lê `source()` passa a ler uma `bronze_*` (cópia fiel, `select *`) da mesma pasta e vira `silver_*`. O que só limpa, deduplica ou deriva dentro da mesma fonte fica Silver em `transferegov/`. O que aplica regra de produto (quem conta em cada cota, flags, cobertura, distribuição) vira Gold `eixo2_meta3_*` em `data_products/cultura_em_numeros/`, lendo Silver e Gold do próprio produto. O único cruzamento entre fontes (BB Ágil × plano de ação) vira `int_bbagil_transferegov`. A cadeia do BB Ágil continua `enabled=false`, como hoje.

**Tech Stack:** dbt-core 1.10 (Postgres), macros do projeto (`coalesce_por_nome`, `origem_da_bronze`, `normaliza_documento`, `parse_valor`, `ano_edital`, `sem_acento`), `verificar.py` da skill `arquitetura-lakehouse-minc`, pytest, `make docs-collect`.

## Global Constraints

- Regras: [ADR 0010](../../adr/0010-camadas-e-schemas-do-data-lakehouse.md) e [ADR 0015](../../adr/0015-produtos-em-data-products-e-gold-lendo-gold.md); a receita é `.claude/skills/arquitetura-lakehouse-minc/references/migracao.md`. Em caso de dúvida entre este plano e o ADR, o ADR vence.
- **Nome e pasta mudam, número não.** Nenhum `where`, `case`, `join` ou cast é alterado. O que muda em cada SQL é só: `source()` → `ref()`/`origem_da_bronze()`, nome dos `ref()`, e a linha `config` de materialização.
- Regra de negócio **não sobe nem desce de camada** neste PR, mesmo que o ADR 0015 peça (é "mudança de regra", outro tipo de PR). Onde um modelo mistura limpeza e regra, ele vai inteiro para a camada da regra (Gold) e o PR registra a dívida.
- `coalesce(..., false)` dos golds fica como está (aviso R6 do script; corrigir é mudança de regra).
- Materialização: pasta de fonte é `view` por padrão; modelo que hoje é `table` declara `{{ config(materialized='table') }}` no próprio arquivo com o motivo. Produto é `table` por padrão.
- Nada de credencial em arquivo versionado. Os JSON e as contagens de validação **não** são commitados.
- Toda silver que usa `coalesce_por_nome` segue o padrão do PR #87: `{% set src = origem_da_bronze('bronze_x') if execute else ref('bronze_x') %}` e `from {{ ref('bronze_x') }}`. Nunca `source()` numa silver.
- Commits em Conventional Commits, um por task, terminando com `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- Comandos dbt rodam com `.venv/bin/dbt` a partir de `dbt/minc/`. `dbt parse` não conecta no banco. `make test`, `make format`, `make lint` e `make docs-collect` precisam do `make setup` feito (poetry).
